# 自动复盘模块 - 业务需求细化文档

## 一、业务目标

### 1.1 核心目标
每6小时自动复盘一次，系统性地检讨过去6小时内的交易历史，通过复盘总结经验、检讨错误，提升交易系统的持续改进能力。

**复盘层次定位**（参考量化交易系统三层复盘架构）：
- **Level 1: 交易执行复盘**：已在交易执行时记录（DecisionRecord中的ExecutionLog）
- **Level 2: 策略表现复盘**：**我们的6小时复盘主要覆盖这个层次**
  - 策略有效性评估
  - 市场适应性分析
  - 规则遵守情况检查
- **Level 3: 系统级复盘**：建议后续增加（每日/每周复盘）
  - 系统性问题识别
  - 规则优化建议
  - 长期趋势分析

### 1.2 业务价值
- **错误识别与纠正**：及时发现并记录违反约束、时机错误、判断偏差等问题
- **成功模式提取**：识别有效的交易策略和市场条件组合
- **规则优化依据**：为系统提示词(prompt)的优化提供数据支撑
- **风险预警**：识别潜在的系统性问题，提前预警
- **持续改进**：基于数据驱动的复盘结果，持续优化交易系统

### 1.3 复盘框架（参考5步实践框架）
采用结构化的5步复盘框架，确保复盘的系统性和完整性：

1. **明确操作风格**：确保复盘与交易风格一致（风险调整后收益最大化）
2. **研判市场情绪**：理解市场环境对交易的影响（趋势/震荡/高波动/低波动/弱势市场）
3. **分析交易数据**：量化分析交易表现（基础统计、风险指标、多维度分析）
4. **总结经验教训**：识别错误模式和成功模式（硬约束违反、风险控制问题、成功策略）
5. **优化交易策略**：基于复盘结果改进系统（Prompt修正、规则优化、参数调整）

## 二、数据源分析

### 2.1 可用数据源

#### 2.1.1 决策日志 (`logger/decision_logger.go`)
- **位置**：`decision_logs/` 目录下的JSON文件
- **内容**：
  - 每个决策周期的完整信息（Cycle Number）
  - AI思维链（CoTTrace）- 决策推理过程
  - 决策JSON - 具体交易决策
  - 账户状态快照（TotalBalance, AvailableBalance, PositionCount等）
  - 持仓快照（EntryPrice, MarkPrice, UnrealizedProfit等）
  - 执行结果（Success, ErrorMessage）
  - 时间戳（Timestamp）

#### 2.1.2 交易历史记录 (`trade_history`)
- **位置**：SQLite数据库 `trade_history` 表
- **内容**：
  - 每笔交易的执行记录（开仓/平仓）
  - 成交价格、数量、杠杆
  - 盈亏（PnL）
  - 手续费
  - 交易所订单ID、交易ID
- **用途**：
  - 用于日常查询和历史分析
  - 用于基础统计和风险指标计算
- **注意**：这是系统内部记录，可能与DEX实际数据有偏差，复盘时应使用DEX独立数据源进行验证

#### 2.1.3 DEX独立数据源（新增 - 想法1）
- **目的**：验证决策是否有效在DEX执行，发现执行偏差
- **实现**：每次复盘时从DEX重新拉取交易数据
- **数据源**：`HyperliquidFillsProvider` - 从DEX API拉取
- **内容**：
  - DEX实际成交记录（独立于系统内部记录）
  - 实际成交价格、数量
  - 实际手续费、资金费
  - 交易所订单ID、交易ID、交易哈希
- **用途**：
  - 验证决策执行有效性
  - 量化执行偏差（滑点、时间差）
  - 发现未预期费用（资金费、额外手续费）
  - 识别系统bug（订单未执行但记录为成功）

#### 2.1.4 交易分析数据 (`trade_analytics`)
- **位置**：基于 `trade_history` 的统计分析
- **内容**：
  - 胜率、盈亏比、夏普比率
  - 最大回撤、波动率
  - 币种表现统计
  - 连续统计（连胜/连亏）

### 2.2 数据时间范围与关联方式

#### 2.2.1 复盘窗口定义
- **复盘窗口**：过去6小时
- **数据查询**：基于 `Timestamp` 字段过滤
- **决策周期数**：约120个周期（假设每3分钟一个周期）

#### 2.2.2 复盘窗口边界处理（已明确）
- **统计范围**：只统计在复盘窗口内**完整完成**的交易（开仓+平仓都在窗口内）
- **边界处理逻辑**：
  - 如果窗口开始时间点的第一笔交易是`close`操作，需要追溯到上一个窗口找到对应的`open`操作
  - 如果窗口结束时间点的最后一笔交易是`open`操作，对应的`close`操作在窗口外，则该交易不计入本次复盘
- **未平仓持仓**：复盘窗口内未平仓的交易不计入统计
- **持仓管理检查**：持仓管理检查不包括未平仓的持仓（仅检查已完成的交易）

#### 2.2.3 数据关联方式（已明确）
- **决策日志与交易历史关联**：
  - **主要方式**：使用时间戳关联（时间窗口容差：1分钟）
    - 决策日志的 `Timestamp` 是决策时间（AI做出决策的时间）
    - 交易历史的 `Timestamp` 是交易执行时间（DEX成交时间）
    - 根据经验，时间差不会超过1分钟
  - **备选方式**：如果时间戳匹配失败，使用 `ExchangeOrderID` 或 `ExchangeTradeID` 匹配
  - **关联失败处理**：标记为未匹配，不阻塞复盘，在报告中标注

## 三、复盘分析维度

### 3.0 多维度分析框架（参考专业交易系统实践）

复盘应该从多个维度进行分析，全面评估交易表现：

**维度1: 时间维度**
- 按小时、按天分析交易分布
- 识别最活跃时段
- 分析不同时段的胜率差异

**维度2: 币种维度**
- 按币种分析表现（已实现）
- 识别最佳/最差币种
- 分析币种特征（市值、波动率、流动性）

**维度3: 策略维度**（需要增强）
- 按策略类型分析（趋势跟踪、均值回归等）
- 按信号类型分析（RSI、MACD、突破等）
- 按市场环境分析（趋势/震荡/高波动）

**维度4: 风险维度**（需要增强）
- 按风险水平分析（杠杆、仓位大小）
- 按回撤水平分析
- 按波动率环境分析

**维度5: 关联分析**（需要增强）
- 决策日志 → 交易历史关联
- **决策 → DEX交易关联**（新增 - 想法1）：验证决策是否有效在DEX执行
- 交易 → 市场数据关联
- 错误 → 上下文关联

### 3.1 交易表现分析

#### 3.1.0 标准化指标输出（新增 - 想法2）

除了传统的performance分析，还应该输出标准化指标，用于量化AI遵循度和决策质量：

**指标类别**：

1. **规则违反指标（Rule Violation Metrics）**
   - 硬约束违反率：违反硬约束的决策数 / 总决策数
   - 风险控制违反率：违反风险控制规则的决策数 / 总决策数
   - 持仓管理违反率：违反持仓管理规则的决策数 / 总持仓决策数
   - 规则违反严重程度分布：Critical/High/Medium/Low分布

2. **决策方向后验指标（Decision Direction Post-Hoc Metrics）**（已明确）
   - 方向准确率：方向正确的决策数 / 总决策数
   - 方向准确度：方向正确的决策的平均盈亏 vs 方向错误的决策的平均盈亏
   - 方向一致性：决策方向与市场趋势的一致性
   - **方向判断逻辑**：决策中提出的方向判断关键词 vs 解析来的三到五个周期的实际市场表现方向之间的比较
   - **时间窗口**：决策之后的三到五个决策log中的实际市场表现
   - **数据来源**：使用决策日志中的市场数据快照，避免额外拉取历史价格数据

3. **AI遵循度指标（AI Compliance Metrics）**（已明确）
   - Prompt规则遵循率：遵循prompt规则的决策数 / 总决策数
   - 规则遵循度分布：不同规则的遵循率
   - **实施说明**：
     - 需要在设计阶段明确目标prompt可以提取哪些遵循指标，建立指标系统然后再分析
     - 目前的目标prompt是 `lean_optimized copy.txt`
     - 自我纠正有效性：暂不实现（Phase 3+）
   - Prompt理解度：AI对prompt的理解程度

4. **DEX验证指标（DEX Validation Metrics）**（新增 - 想法1）
   - 决策执行率：成功执行的决策 / 总决策数
   - 未匹配决策数：决策日志中有但DEX没有的交易
   - 未匹配DEX交易数：DEX有但决策日志没有的交易
   - 平均滑点：|实际价格 - 决策价格| / 决策价格
   - 平均执行延迟：实际执行时间 - 决策时间
   - 费用差异：实际费用 - 预期费用
   - 总资金费：从DEX数据中提取的资金费总和

**指标计算方式**：
- 规则违反指标：基于规则引擎检查决策
- 决策方向后验指标：需要市场数据支持，事后验证
- AI遵循度指标：需要分析AI思维链和Prompt
- DEX验证指标：需要匹配决策与DEX交易数据

#### 3.1.1 基础统计
- **交易笔数**：开仓数、平仓数、完成交易数
- **盈亏统计**：
  - 总盈亏、净盈亏（扣除手续费）
  - 平均盈亏、最大盈利、最大亏损
  - 盈亏分布（盈利/亏损/持平）
- **胜率统计**：
  - 胜率、盈利交易数、亏损交易数
  - 盈亏比（Profit Factor）
- **费用统计**：
  - 总手续费、平均手续费
  - 费用占比（费用/总盈亏）

#### 3.1.2 风险指标
- **回撤分析**：
  - 最大回撤、回撤持续时间
  - 回撤恢复时间
- **波动率**：PnL的标准差
- **夏普比率**：风险调整后收益
- **连续统计**：
  - 最长连胜、最长连亏
  - 当前连续状态

#### 3.1.3 币种表现
- **各币种统计**：
  - 交易次数、胜率、总盈亏
  - 平均盈亏、最大盈利、最大亏损
- **最佳/最差币种**：识别表现最好和最差的币种

### 3.2 错误识别与分析

**风险事件分类**（参考风险管理实践）：

- **Category 1: 规则违反（Rule Violations）** - **重点覆盖**
  - 硬约束违反（风险回报比、杠杆限制等）
  - 风险控制规则违反
  - 系统配置错误

- **Category 2: 执行错误（Execution Errors）**
  - 订单执行失败（已在执行日志中记录）
  - 价格偏差过大
  - 滑点异常

- **Category 3: 策略失效（Strategy Failures）** - **重点覆盖**
  - 策略在特定市场环境下失效
  - 参数设置不当
  - 信号质量下降

- **Category 4: 系统故障（System Failures）**
  - 数据延迟或缺失（需要系统监控）
  - API调用失败
  - 系统崩溃

#### 3.2.1 硬约束违反（Category 1）
- **风险回报比**：
  - 检查是否满足 ≥3.0:1 的要求
  - 识别违反的交易及其原因
- **杠杆限制**：
  - 检查是否超过系统配置限制
  - 识别配置错误（如使用推荐杠杆但系统限制更低）
- **止损/止盈方向**：
  - 多仓：stop_loss < entry < take_profit
  - 空仓：take_profit < entry < stop_loss
- **置信度要求**：
  - 开仓置信度是否 ≥70
  - Sharpe < 0 时是否 ≥85

#### 3.2.2 风险控制问题（Category 1 & 3）
- **止损设置问题**：
  - 止损是否过窄（导致虚假触发）
  - 是否考虑了市场噪音（BTC/ETH最小0.3-0.5%）
  - 杠杆调整后的账户风险是否合理（≤8%）
- **时间稳定性问题**：
  - 是否基于超短期信号交易（单根K线、分钟级变动）
  - 信号是否在执行延迟后仍然有效（10+分钟）
- **市场环境适应**：
  - 是否在震荡市场频繁交易
  - 是否在弱势市场过度交易
  - 是否根据市场环境调整参数

#### 3.2.3 持仓管理问题（Category 3）
- **入场假设验证**：
  - 是否在入场假设失效时及时退出
  - 是否过度重视"价格仍在入场价之上"而忽略假设失效
  - RSI/MACD/趋势线变化是否被正确识别
- **止损距离管理**：
  - 是否在止损距离<0.2%时提前退出
  - 是否在盈利时上移止损保护利润
  - 是否在入场假设失效时上移止损至入场价
- **"真正变化"识别**：
  - 是否满足"真正变化"条件但未快速响应
  - 是否误判为"正常波动"而继续持有
  - 规则优先级是否正确（入场假设失效 > 真正变化 > 时间窗口）

#### 3.2.4 时机错误（Category 3）
- **开仓时机**：
  - 是否在震荡期间频繁交易
  - 是否逆趋势交易
  - 是否在前一个仓位被止损后立即开新仓位
- **平仓时机**：
  - 是否过早平仓，错过大行情
  - 是否过晚平仓，盈利转为亏损
  - 是否在技术位被破坏时及时退出

#### 3.2.5 系统性偏差（Category 3）
- **重复错误模式**：
  - 是否反复违反同一约束
  - 是否重复系统配置错误
  - 是否重复止损触发过于频繁
- **判断偏差**：
  - 是否总是高估信号强度
  - 是否总是低估市场波动性
  - 是否在"极端"信号时放松约束
  - 是否忽略杠杆敏感度

#### 3.2.6 AI决策质量分析（新增，参考AI系统评估实践）
- **推理质量评估**：
  - 思维链的逻辑性
  - 决策依据的充分性
  - 约束检查的完整性
- **决策一致性分析**：
  - 相似市场条件下的决策一致性
  - 规则应用的稳定性
- **自我纠正有效性**：
  - 历史错误的学习效果
  - 自我纠正是否有效
- **Prompt效果评估**：
  - 规则遵守率趋势
  - 决策质量变化
  - 错误模式变化

### 3.3 成功模式识别

#### 3.3.1 有效策略识别
- **市场条件组合**：
  - 哪些市场条件组合（趋势/震荡/高波动/低波动）表现最好
  - 不同市场环境下的最佳参数设置
- **信号类型**：
  - 哪些技术指标组合更可靠
  - 哪些信号类型胜率更高
- **币种特征**：
  - 哪些币种表现更好
  - 不同币种的最佳杠杆和止损设置

#### 3.3.2 成功交易特征
- **入场特征**：
  - 成功交易的市场条件
  - 成功交易的技术指标组合
  - 成功交易的置信度分布
- **持仓管理**：
  - 成功交易的持仓时长
  - 成功交易的止损/止盈设置
  - 成功交易的动态止损调整

### 3.4 市场环境分析

#### 3.4.1 市场状态识别
- **趋势方向**：上涨/下跌/横盘
- **波动率环境**：高/正常/低
- **成交量特征**：高/正常/低
- **弱势市场**：是否处于弱势市场（Sharpe < 0）

#### 3.4.2 环境与表现关联
- **不同市场环境下的表现**：
  - 趋势市场的表现 vs 震荡市场
  - 高波动率 vs 低波动率
  - 弱势市场 vs 正常市场
- **环境适应性**：
  - 系统是否根据市场环境调整策略
  - 调整是否有效

## 四、复盘报告结构

**参考标准**：专业交易公司的标准复盘报告结构

### 4.1 执行摘要（Executive Summary）
- **复盘时间范围**：开始时间 - 结束时间
- **复盘层次**：策略表现复盘（Level 2）
- **核心发现**：3-5个最重要的发现（错误/成功模式）
- **关键结论**：整体评估和改进建议
- **行动建议**：需要立即采取的行动

### 4.2 表现概览（Performance Overview）
- **基础统计**：交易笔数、盈亏、胜率、盈亏比
- **风险指标**：最大回撤、波动率、夏普比率
- **币种表现**：最佳/最差币种
- **与基准对比**：如果有历史基准，进行对比分析

### 4.3 详细分析（Detailed Analysis）

#### 4.3.1 错误分析
- **硬约束违反**：
  - 违反类型、次数、涉及交易
  - 具体案例和原因分析
- **风险控制问题**：
  - 止损设置问题、时间稳定性问题
  - 具体案例和改进建议
- **持仓管理问题**：
  - 入场假设验证问题、止损距离管理问题
  - "真正变化"识别问题
- **时机错误**：
  - 开仓/平仓时机问题
  - 系统性偏差识别

#### 4.3.2 成功模式
- **有效策略**：市场条件组合、信号类型、币种特征
- **成功交易特征**：入场特征、持仓管理特征

## 六、业务规则细化

### 6.1 错误识别规则

#### 6.1.1 硬约束违反检查
- **风险回报比检查**：
  - 计算：(take_profit - entry) / (entry - stop_loss) 对于多仓
  - 计算：(entry - take_profit) / (stop_loss - entry) 对于空仓
  - 必须 ≥ 3.0:1
- **杠杆限制检查**：
  - 查询系统配置（btcEthLeverage, altcoinLeverage）
  - 检查决策中的杠杆是否超过限制
- **止损/止盈方向检查**：
  - 多仓：stop_loss < entry < take_profit
  - 空仓：take_profit < entry < stop_loss
- **置信度检查**：
  - 开仓置信度 ≥ 70
  - Sharpe < 0 时置信度 ≥ 85

#### 6.1.2 风险控制检查
- **止损宽度检查**：
  - BTC/ETH：最小0.3-0.5%
  - 大市值山寨币：最小0.5-0.7%
  - 其他：最小0.7-1%
- **账户风险检查**：
  - (价格止损距离% × 杠杆) ≤ 8%
- **时间稳定性检查**：
  - 是否基于单根K线模式
  - 是否基于分钟级变动
  - 信号是否在执行延迟后仍然有效（10+分钟）

#### 6.1.3 持仓管理检查
- **入场假设验证**：
  - 检查入场假设的核心逻辑是否失效
  - RSI入场假设：RSI从改善状态重新暴跌>30%
  - MACD入场假设：MACD从正转负（多仓）或从负转正（空仓）
  - 趋势入场假设：价格跌破关键趋势线并持续>3根K线
- **止损距离管理**：
  - 止损距离<0.2%时是否提前退出
  - 盈利≥1%时是否上移止损
  - 入场假设失效时是否上移止损至入场价
- **"真正变化"识别**：
  - 价格突破关键技术位（幅度>0.15%）
  - 多个指标同步变化（至少2个）
  - 成交量激增（>2倍）
  - 是否在满足条件时快速响应（5-10分钟）

### 6.2 成功模式提取规则

#### 6.2.1 市场条件组合
- **趋势市场**：
  - 价格创出更高的高点/更低低点
  - 方向明确
- **震荡市场**：
  - 价格在支撑/阻力之间波动
- **高波动率**：
  - ATR > 20周期平均值的1.5倍
- **低波动率**：
  - ATR < 20周期平均值的0.7倍
- **弱势市场**：
  - 整体市场处于下跌趋势
  - 多数币种价格低于EMA20
  - MACD为负值

#### 6.2.2 信号类型
- **技术指标组合**：
  - RSI + MACD + EMA组合
  - 成交量确认
  - 多时间框架确认
- **信号强度**：
  - 置信度分布
  - 风险回报比分布

### 6.3 报告生成规则

#### 6.3.1 报告优先级
- **Critical错误**：必须包含在报告中
- **High错误**：优先包含
- **Medium/Low错误**：选择性包含

#### 6.3.2 案例选择
- **错误案例**：选择最典型、影响最大的案例
- **成功案例**：选择胜率高、盈亏比大的案例

## 十二、关键风险指标监控（参考风险管理实践）

### 12.1 关键风险指标（KRI - Key Risk Indicators）

#### 指标1: 最大回撤（Maximum Drawdown）
- **阈值**：> 25% 触发预警
- **复盘重点**：分析回撤原因、持续时间、恢复时间

#### 指标2: 波动率（Volatility）
- **阈值**：超过历史平均值的1.5倍
- **复盘重点**：分析波动率增加的原因

#### 指标3: 夏普比率（Sharpe Ratio）
- **阈值**：< 0 触发熔断机制
- **复盘重点**：分析夏普比率下降的原因

#### 指标4: 连续亏损（Consecutive Losses）
- **阈值**：连续2次亏损触发暂停
- **复盘重点**：分析连续亏损的模式

### 12.2 风险事件响应

当识别到风险指标异常时，复盘报告应该：
1. **详细分析异常原因**：为什么发生？
2. **评估影响范围**：影响哪些交易？
3. **提供改进建议**：如何避免？
4. **建议行动**：是否需要立即采取行动？

## 十四、错误处理与容错（新增）

### 14.1 复盘失败的处理机制（已明确）

#### 14.1.1 错误分类
- **致命错误**：导致复盘无法继续（例如数据库连接失败、DEX数据拉取失败）
- **部分错误**：部分数据无法获取，但可以继续复盘（例如部分决策日志文件损坏）
- **警告**：数据质量有问题，但不影响复盘（例如数据不完整）

#### 14.1.2 错误处理策略（已明确）
- **致命错误**：记录错误日志，跳过本次复盘，等待下次定时触发（不自动重试）
- **部分错误**：继续复盘，在报告中标注缺失的数据
- **警告**：继续复盘，在报告中标注数据来源

#### 14.1.3 具体错误场景
- **决策日志文件损坏**：标记为部分错误，继续复盘，在报告中标注
- **数据库查询失败**：标记为致命错误，记录错误日志，跳过本次复盘
- **DEX数据拉取失败**：标记为致命错误，记录错误日志，跳过本次复盘（不降级）
- **规则检查异常**：标记为部分错误，继续复盘，在报告中标注

### 14.2 数据质量检查

#### 14.2.1 数据完整性检查
- 复盘前检查决策日志文件是否存在、是否可读
- 检查交易历史数据是否完整（开仓是否有对应的平仓？）
- 检查DEX数据是否可用

#### 14.2.2 数据一致性检查
- 检查决策日志和交易历史的时间范围是否匹配
- 检查DEX数据和系统内部记录是否一致（如果DEX数据可用）

#### 14.2.3 数据质量报告
- 在复盘报告中包含数据质量评估
- 如果数据质量有问题，明确标注

### 14.3 监控与告警（已明确）
- **监控方式**：通过日志记录复盘执行状态
- **告警机制**：通过日志记录（不实现独立的告警系统）
- **日志内容**：
  - 复盘开始/结束时间
  - 各阶段执行耗时
  - 错误信息（如果有）
  - 数据质量警告（如果有）

## 十三、数据验证与标准化指标（新增）

### 13.1 DEX独立数据源验证（想法1）

#### 13.1.1 核心目标
- 验证decision log中的决策是否有效在DEX执行
- 发现时间差、滑点、未预期的资金费、手续费等问题
- 确保复盘基于真实的DEX数据，而非系统内部记录

#### 13.1.2 实施阶段

**Phase 1: 决策执行验证**
- 从DEX拉取指定时间范围的交易数据
- 匹配决策与DEX交易（通过ExchangeOrderID、时间窗口、币种+方向）
- 计算决策执行率：成功执行的决策 / 总决策数
- 识别未匹配的决策和DEX交易

**Phase 2: 执行质量分析**
- 量化执行偏差：
  - 平均滑点：|实际价格 - 决策价格| / 决策价格
  - 平均执行延迟：实际执行时间 - 决策时间
  - 费用差异：实际费用 - 预期费用
  - 数量差异：实际数量 - 决策数量

**Phase 3: 成本分析**
- 从DEX数据中提取资金费
- 计算总成本（手续费 + 资金费）
- 评估成本对收益的影响

#### 13.1.3 技术实现
- **数据拉取**：
  - 使用 `HyperliquidFillsProvider` 从DEX API拉取数据
  - 拉取指定时间范围的交易数据（复盘窗口）
  - 不保存到数据库，仅用于复盘验证
- **数据匹配算法**：
  - **优先级1**：通过ExchangeOrderID匹配（最准确）
  - **优先级2**：通过时间窗口+币种+方向匹配（备选）
    - 时间窗口：决策时间前后5-10分钟
    - 币种：完全匹配
    - 方向：long/short匹配
  - **优先级3**：通过数量+价格范围匹配（最后备选）
    - 数量差异：< 5%
    - 价格差异：< 1%
  - **匹配失败处理**：
    - 未匹配的决策：标记为"执行失败"或"未找到对应DEX交易"
    - 未匹配的DEX交易：标记为"非系统发起"或"需要人工确认"
  - **部分匹配处理**：
    - 一个决策对应多个DEX交易：合并计算（累加数量、平均价格）
    - 多个决策对应一个DEX交易：标记为"系统重试"或"需要人工确认"
- **错误处理机制**：
  - **API限流处理**：
    - 检测到限流时，等待后重试（指数退避）
    - 最大重试次数：3次
    - 重试间隔：1秒、2秒、4秒
  - **数据拉取失败处理**（已明确）：
    - **失败策略**：DEX数据拉取失败时，直接报错停止本轮复盘（不降级到系统内部记录）
    - 网络错误：重试3次后，如果仍然失败，记录错误日志并停止复盘
    - API错误：记录错误日志并停止复盘
    - 数据不完整：记录警告，如果关键数据缺失，停止复盘
  - **性能优化**：
    - 并行拉取多个币种的数据（如果API支持）
    - 缓存最近拉取的数据（避免重复拉取）
    - 增量拉取（只拉取复盘窗口内的数据）

#### 13.2.3 技术实现
- **规则引擎设计**：
  - **规则定义方式**：在代码中明确定义规则（推荐），而非从prompt中NLP提取
  - **规则格式**：
    ```go
    type Rule struct {
        ID          string    // 规则ID
        Name        string    // 规则名称
        Type        string    // 规则类型：hard_constraint/risk_control/position_management
        Severity    string    // 严重程度：critical/high/medium/low
        CheckFunc   func(decision *Decision) bool  // 检查函数
        Description string    // 规则描述（从prompt中提取，用于展示）
    }
    ```
  - **规则优先级**：
    - Critical：硬约束违反（必须检查）
    - High：风险控制规则（优先检查）
    - Medium：持仓管理规则（常规检查）
    - Low：时机错误（可选检查）
  - **规则提取**：
    - Prompt中的规则描述用于展示和验证
    - 规则检查逻辑在代码中实现
    - 可以手动维护规则与prompt的映射关系
  - **规则引擎设计**（架构建议）：
    - **插件化设计**：采用接口设计，支持规则的动态注册
    ```go
    type RuleChecker interface {
        Check(decision *DecisionRecord) ([]Violation, error)
        GetRuleID() string
        GetSeverity() string
    }
    ```
    - 不同类型的规则检查器独立实现（硬约束检查器、风险控制检查器、持仓管理检查器）
    - 支持规则的动态注册和优先级排序
    - **规则定义方式**：
      - **核心规则**（硬约束）：在代码中定义，确保稳定性
      - **业务规则**（风险控制、持仓管理）：可以配置化，支持动态调整
      - **分析规则**（AI决策质量分析）：可以作为插件，支持扩展
- **指标计算器**：
  - 基于规则引擎检查每个决策
  - 统计违反次数和类型
  - 计算违反率和分布
- **市场数据提供者**（用于方向后验指标）：
  - **数据需求**：
    - 价格走势数据（用于判断方向是否正确）
